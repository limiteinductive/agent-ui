Designing Resilient Frontends: Lessons From Shipping at Scale

Our web client now handles millions of sessions a week across flaky networks, old devices, and third-party outages. Here is what actually held up.

Mara Ellison Staff Engineer · November 18, 2026 · 12 min read

Most frontend architecture advice assumes a fast connection, a current browser, and a backend that answers every request in under two hundred milliseconds. Production rarely agrees. Over the past year we rebuilt our client to assume the opposite, and the results changed how we think about what a "working" page means.

Start from the failure, not the happy path

Our first draft was organized around the screens people see when everything works. Every component fetched its own data, rendered a spinner, and hoped for the best. When an upstream service slowed down, the spinners stayed up for thirty seconds and then turned into blank panels with no explanation.

We flipped the process. For each feature we now list the states it can be in before writing any markup: fresh data, stale data, partially loaded, offline, rate-limited, and unauthorized. The design review does not close until each state has a defined appearance and a defined next action for the user.

A spinner is a promise that something will happen. Make sure you can keep it.

Internal design review notes, Q3

Separate what you show from what you fetched

The biggest single improvement came from putting a local, normalized store between the network and the components. Components read from the store and never from the wire. The store records when each entity was last confirmed by the server, which lets us show cached values immediately and label them honestly when they are old.

Writing to the store is optimistic by default. A user action updates the local state at once, a queued request goes to the server, and a reconciliation step reverts or merges the result. Users stopped reporting "lost changes" almost entirely once this landed.

Retries need budgets, not just backoff

Exponential backoff sounds sensible until a thousand clients retry in lockstep after a deploy. We now give each session a retry budget, a fixed number of attempts per rolling minute, and add jitter to every delay. When the budget is empty the client stops asking and shows the last known good state with a clear refresh control.

This has a useful side effect: the budget is observable. We alert on budget exhaustion per route, which tells us about a degraded dependency long before error rates cross a dashboard threshold.

Hydrate what the user can touch

Full-page hydration was the other bottleneck. On low-end Android devices, the main thread spent more time booting our component tree than the user spent waiting for content. We now server-render the entire page and hydrate interactive islands on demand, starting with whatever is in or near the viewport. Static sections such as article bodies and footers never hydrate at all.

The discipline this requires is less about tooling and more about ownership. Every island needs a named owner, a size budget, and a documented reason for needing JavaScript in the first place.

What we would do differently

If we were starting over, we would introduce the store and the failure-state checklist on day one instead of retrofitting them after the first major incident. We would also measure real-user performance from the first sprint, not the last. Lab numbers flattered us for months.

Resilience is not a feature you add at the end. It is the set of decisions that determine what your users see when the rest of the system is having a bad day.
