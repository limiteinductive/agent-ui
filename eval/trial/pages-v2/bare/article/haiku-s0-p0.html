Designing Resilient Frontends: Lessons from Shipping at Scale

What we learned rebuilding our frontend architecture to survive flaky networks, partial outages, and a team that grew from six engineers to sixty.

Maya Chen Staff Engineer · November 14, 2026 · 12 min read

Two years ago, our customer dashboard was a single-page application that worked beautifully on fast office Wi-Fi and fell apart everywhere else. A subway commute could leave a user staring at a spinner. A failed analytics request could blank out an entire panel. A slow CDN region could make the whole product feel broken. We didn't have a single catastrophic bug. We had a thousand small assumptions that the network would behave.

This article describes how we changed those assumptions. It is not a story about adopting a new framework. Most of the wins came from treating the browser as a hostile, unreliable environment and designing each layer to degrade gracefully.

Start from the failure modes

Before writing any code, we spent two weeks cataloguing how our product actually failed. We pulled six months of error reports, session replays, and support tickets, then grouped them into categories. The biggest bucket was not JavaScript exceptions. It was requests that hung, responses that arrived out of order, and components that rendered stale data after a user had already moved on.

That exercise changed our priorities. Instead of asking "how do we make this feature faster," we started asking "what should the user see when this specific dependency is unavailable?" Every screen got a short written answer to that question, and those answers became acceptance criteria.

Reliability is not a property you add at the end. It is the shape of every decision you make about loading, caching, and showing data.

Maya Chen, in our internal architecture review

Separate what is loaded from what is shown

The most useful refactor we made was splitting our data layer into two concerns. The first is a cache that holds the last known good value for every query, keyed by its parameters. The second is a presentation layer that always renders from the cache first and only then reconciles with the network. Users almost never see an empty screen after their first visit, even when the network is gone.

The pattern is simple to describe and surprisingly easy to get wrong. Stale data must be visibly marked as stale, otherwise users will make decisions based on numbers that no longer reflect reality. We added a small, consistent indicator and a timestamp, and we made sure every component that displays cached data uses the same one.

Here is the core of the fetch wrapper that every feature now uses:

export async function resilientFetch<T>(
  key: string,
  loader: (signal: AbortSignal) => Promise<T>,
  { timeoutMs = 8000, retries = 2 }: Options = {}
): Promise<Result<T>> {
  const cached = cache.get<T>(key);

  for (let attempt = 0; attempt <= retries; attempt++) {
    const controller = new AbortController();
    const timer = setTimeout(() => controller.abort(), timeoutMs);
    try {
      const data = await loader(controller.signal);
      cache.set(key, data);
      return { status: "fresh", data };
    } catch (err) {
      if (attempt === retries) break;
      await sleep(backoff(attempt));
    } finally {
      clearTimeout(timer);
    }
  }

  return cached
    ? { status: "stale", data: cached.value, updatedAt: cached.updatedAt }
    : { status: "unavailable" };
}

Notice what the function does not do. It never throws into the render tree. It returns a discriminated union that forces each consumer to decide how to present fresh, stale, and unavailable states. That decision is where most of our resilience now lives.

Make timeouts a product decision

Default timeouts in browsers are effectively infinite from a user's perspective. We set explicit budgets for each category of request, and we tied them to the experience we wanted rather than to whatever number seemed reasonable. A search suggestion that takes more than 800 milliseconds is worse than no suggestion at all, so it gets a short budget and silently falls back. A checkout confirmation gets a much longer budget, because abandoning it is far more expensive.

Every timeout is recorded as a metric tagged with the screen and the dependency. Within a month, the dashboard showed us exactly which third-party scripts and internal services were causing the most user-visible delay, and we had concrete numbers to bring to vendor conversations.

Isolate failures at the component boundary

Error boundaries existed in our codebase before this project, but they were used sparingly, usually at the root. A single failing widget could take down the entire page. We moved boundaries down to every independent panel, so a broken revenue chart no longer prevents a user from reading their invoices.

The rule we settled on is simple: any component that depends on a network resource must be wrapped in a boundary that owns its own fallback. The fallback is designed, not generic. It explains what is unavailable, offers a retry, and links to a status page when one exists.

What we would do differently

If we were starting again, we would invest in observability before we invested in architecture. We built most of the resilience layer blind, and we could only tune it after we had good data about how it behaved in the wild. We would also write the degraded-state designs earlier, because they surfaced product questions that engineering could not answer alone.

Finally, we would test with real bad networks much sooner. Throttling in developer tools is a useful start, but nothing replaces a phone on a train with three bars of signal. Our most valuable bug reports in the last year came from people who were deliberately trying to break the app on slow connections.

Resilience is not a feature we shipped and moved on from. It is a habit we practice in every review, every design, and every postmortem. The good news is that the habit compounds. Each fallback we design makes the next one faster to build, and each outage we survive quietly becomes part of how the team thinks.
