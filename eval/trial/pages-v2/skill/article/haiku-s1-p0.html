Designing Offline-First Web Apps Without the Pain

A practical guide to local-first data, sync conflicts, and the small decisions that make a web app keep working when the network does not.

 Mira Okafor Staff Engineer · November 14, 2026 · 9 min read

Most web applications are built on an unspoken assumption: the server is reachable, and the user is one request away from their data. That assumption holds in an office on fiber. It stops holding on a train, in an elevator, or on a conference Wi-Fi network that drops every few minutes. When it breaks, the app usually fails in the same few ways: a spinner that never resolves, a form that clears itself after submission, or a list that quietly shows stale results.

Offline-first is a different starting point. Instead of treating local storage as a cache that sometimes helps, you treat the device as a first-class replica of the data. The interface reads and writes locally, and synchronization becomes a background concern that runs when a connection is available. The shift sounds small, but it changes almost every decision downstream.

Start with the local source of truth

The first decision is where the authoritative copy of your data lives while the user is working. For most apps, that means an embedded database in the browser, such as IndexedDB wrapped by a small query layer. Reads come from that store, so the UI never waits on a network round trip to show something the user already created.

Writes follow the same pattern. When a user saves a note, the app records the change locally with a stable identifier and a timestamp, then marks it as pending. The interface updates immediately. A separate sync loop picks up pending changes and sends them to the server when it can.

If the user can see it, the device should be able to change it, even when the server cannot be reached.

Make writes idempotent

Retries are unavoidable. A request can reach the server, succeed, and still lose its response on the way back. If the client retries blindly, the server may apply the same change twice. The fix is to give every mutation a client-generated identifier and have the server treat repeated identifiers as no-ops.

A small retry helper with exponential backoff covers most transient failures. Keep the delay bounded, add jitter so many clients do not retry in lockstep, and stop retrying on errors that a retry cannot fix.

async function sendWithRetry(op, attempts = 5) {
  for (let i = 0; i < attempts; i++) {
    try {
      const res = await fetch("/api/sync", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify(op),
      });
      if (res.ok) return await res.json();
      if (res.status < 500) throw new Error(res.status);
    } catch (err) {
      if (i === attempts - 1) throw err;
    }
    const jitter = Math.random() * 250;
    await new Promise((r) => setTimeout(r, 2 ** i * 300 + jitter));
  }
}

Choose a retry policy you can explain

Teams often add retries with no clear rule about which errors deserve another attempt. Write the rule down. Network failures and server errors in the 5xx range are usually worth retrying. Client errors such as validation failures are not, and retrying them only delays the moment someone notices the bug.

Resolve conflicts on purpose

Once two devices can edit the same record while disconnected, conflicts are inevitable. The question is not whether they happen but what the system does when they do. Last-write-wins is simple and sometimes correct, but it silently discards edits. For structured data, field-level merges preserve more intent. For free text, some teams keep both versions and ask the user to reconcile.

Whatever strategy you pick, surface it. A user who sees "This note was changed on another device. Review changes" can recover. A user who loses a paragraph without knowing it will stop trusting the app.

Tell the user what is happening

Offline support fails quietly when the interface hides sync state. Show whether a change is saved locally, queued, or confirmed by the server. A small indicator next to each item is often enough. Avoid blocking the entire screen for a background operation, because that undoes the benefit of working locally in the first place.

Finally, test the unhappy paths on purpose. Throttle the network in developer tools, go offline in the middle of a save, and reload the page with a queue of pending writes. Those scenarios reveal the bugs that a happy-path demo never will.
