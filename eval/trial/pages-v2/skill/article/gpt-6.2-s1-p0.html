Designing for the trailhead, where the signal ends

A weekend without reception changed how we think about saving drafts, showing sync status, and picking up where you left off.

Maya Chen September 18, 2026 · 5 min read

At the trailhead on Saturday, I opened our trip journal to record a washed-out footbridge. I typed two sentences, put my phone away, and kept walking. At lunch I opened the app again. The entry was gone. Our save button had sent a request, the request had stalled, and the draft had been living in memory the whole time.

Save the note where it was written

Back at my desk, I could reproduce the bug without a mountain. I turned on airplane mode, entered a note, and reloaded the page. The team had tested whether failed requests displayed an error. Nobody had checked whether the words were still there after a reload.

We moved the first save into IndexedDB. Once that transaction finishes, the editor can confirm the draft is on the device. A separate upload can run whenever the app has a usable connection. The next test was simple: write a note offline, close the tab, reopen it, and find every word exactly where we left it.

“I’m about to put my phone in my pocket. Will those words be there when I take it out again?”

Show which version is saved

A single “Saved” label became confusing once the laptop and phone could hold different versions. We gave each edit a revision number. The editor compares the visible revision with the last one it stored locally and the last one the server acknowledged.

function draftStatus(edit, local, remote) {
  if (edit !== local) {
    return "Saving on this device…";
  }

  if (edit === remote) {
    return "Synced";
  }

  return "Saved on this device";
}

These three labels cover the normal save path. A local write error gets its own message, and the editor keeps the text visible so the writer can retry or copy it. If an upload fails after the local write, the draft still says it’s saved on this device.

Test the interruptions people actually have

Airplane mode caught the original bug. A throttled connection found another: if I kept typing during an upload, the old response could make my newest changes appear synced. Comparing the acknowledgment with the revision currently visible in the editor fixed the label.

Now we run the same short test before shipping changes to the editor. Start a note offline, close and reopen the tab, reconnect on a slow network, and edit while the upload is still in flight. At each step, we check that the newest text survives and that the status matches where that version is stored.

On the next hike, I recorded the location of a reliable water source. The note was still open when I took my phone out at lunch. It synced that evening while I was unpacking.
