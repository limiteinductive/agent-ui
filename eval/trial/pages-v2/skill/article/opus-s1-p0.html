The Quiet Cost of Layout Shift: Building Interfaces That Hold Still

Users rarely complain about layout shift by name. They just tap the wrong button, lose their place, and trust your product a little less.

Mara Lindqvist Staff Engineer, Design Systems · November 18, 2026

A few months ago our team shipped a redesign of the checkout page. Conversion dipped by almost two percent in the first week. Nothing was broken, every test passed, and the page looked better than ever. It took us an embarrassingly long time to find the culprit: a promotional banner that loaded late and pushed the "Place order" button down by 64 pixels — just as people were reaching for it.

That experience changed how I think about visual stability. It's not a performance metric to optimize once a quarter; it's a property of the interface that you design for from the first sketch.

Why things move in the first place

Nearly every layout shift comes from content whose size the browser did not know ahead of time. The usual suspects are familiar:

  • Images and video without intrinsic dimensions.
  • Web fonts that swap in with different metrics than the fallback.
  • Ads, embeds and banners injected above existing content.
  • Client-rendered components that replace a loading state of a different height.

Each of these is a promise the page fails to keep. The browser lays things out with the best information it has, then the information changes and everything below has to move.

Reserve space, always

The single most effective habit is to give every late-arriving element a box before it arrives. For images, that means writing width and height attributes so the browser can compute an aspect ratio up front. For dynamic regions, it means agreeing on a minimum size with design.

"A stable layout is a form of respect. It tells people the thing they're about to touch will still be there when their finger lands."

Here is a small helper we now use for any slot whose content arrives asynchronously. It measures the placeholder, locks its height, and releases it only after the real content has rendered:

function holdSpace(slot, render) {
  const h = slot.getBoundingClientRect().height;
  slot.style.minHeight = h + "px";

  return Promise.resolve(render(slot))
    .then(() => requestAnimationFrame(() => {
      slot.style.minHeight = "";
    }));
}

It's deliberately boring. The point isn't cleverness; it's making the stable path the easy path for everyone on the team.

Fonts deserve a fallback plan

Font swaps are sneakier because the shift is spread across every line of text. Modern CSS lets you tune the fallback font with size-adjust and the ascent and descent overrides so it occupies almost exactly the same space as the web font. Combined with preloading your primary weight, the swap becomes nearly invisible.

Measure in the field, not just the lab

Lab tools load your page once, on a fast machine, and stop recording early. Real users scroll, open menus, and sit on slow networks where everything arrives in a different order. Collect cumulative layout shift from real sessions and segment it by page and device. The worst offenders are almost never where you expect.

What changed for us

After fixing the banner and auditing our component library for unreserved slots, checkout conversion recovered and then climbed past its old baseline. More importantly, "does this hold still?" became a standard question in design review — right next to "is this accessible?" and "does this work on a small phone?"

Interfaces that hold still feel faster, calmer, and more trustworthy. It's one of the cheapest quality improvements you can make, and your users will never notice it. That's exactly the point.
