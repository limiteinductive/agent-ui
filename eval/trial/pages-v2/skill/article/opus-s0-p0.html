Designing for the Slow Network: Lessons from Shipping Offline-First

What three years of building offline-first web apps taught us about caching, conflict resolution, and telling users the truth about loading.

 Maya Okafor Staff Engineer · November 14, 2026

When we started rebuilding our field-inspection app in 2023, our analytics told a story we had been ignoring for years: nearly 40% of sessions began on a connection slower than 3G, and almost one in ten started with no connection at all. Our users were inspectors working in basements, rural substations and concrete parking garages. For them, "the network" was a rumor.

This post is a collection of what we learned turning a conventional request-response app into one that treats the network as an optimization rather than a requirement. Some of it is technical. A surprising amount of it is about honesty.

Start with the data model, not the cache

The first instinct most teams have is to bolt a service worker onto an existing app and cache API responses. We tried that. It got us a working splash screen and a lot of stale data that users could not distinguish from fresh data.

The shift that actually worked was to make the local database the source of truth for the UI. Every screen reads from IndexedDB. The network's only job is to reconcile that local store with the server whenever it can. Once we made that change, an entire category of loading spinners simply disappeared, because there was nothing to wait for.

  • Reads always hit the local store first and render immediately.
  • Writes go into an outbox table with a client-generated ID.
  • Sync runs in the background and drains the outbox when connectivity returns.

The outbox pattern in practice

The outbox is the heart of the system. Each mutation is recorded as an intent, not a final state, which makes it far easier to replay and to merge. Here is a simplified version of the queue we ship today:

// outbox.js — queue mutations locally, flush when online
export async function enqueue(db, mutation) {
  const entry = {
    id: crypto.randomUUID(),
    createdAt: Date.now(),
    attempts: 0,
    ...mutation,
  };
  await db.put("outbox", entry);
  if (navigator.onLine) flush(db);
  return entry.id;
}

export async function flush(db) {
  const pending = await db.getAll("outbox");
  for (const entry of pending.sort((a, b) => a.createdAt - b.createdAt)) {
    try {
      await fetch("/api/mutations", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify(entry),
      });
      await db.delete("outbox", entry.id);
    } catch {
      await db.put("outbox", { ...entry, attempts: entry.attempts + 1 });
      break; // stop on first failure; keep ordering intact
    }
  }
}

window.addEventListener("online", () => flush(openDb()));

Two details matter more than they look. First, the client generates the ID, so the UI can reference a record before the server has ever seen it. Second, we stop flushing on the first failure. Sending mutations out of order caused more bugs in our first prototype than every other issue combined.

"An offline-first app isn't one that works without the network. It's one that never lies to you about what the network has done."

— From our internal design principles, v2

Conflicts are a product decision

Engineers love to argue about CRDTs versus last-write-wins. In our experience, the right answer depended almost entirely on the field. For free-text notes, we merge. For a checkbox that says "hazard cleared," we never silently overwrite; we surface both values and ask a human.

We ended up categorizing every field in our schema into one of three buckets:

  1. Mergeable — notes, photo collections, tags.
  2. Latest wins — cosmetic fields like a display color or sort order.
  3. Needs review — anything with safety or billing consequences.

That table, written together with our product and compliance teams, was more valuable than any sync library we evaluated.

Honest loading states

Once local reads are instant, the remaining challenge is communicating sync status without nagging. We settled on a small, persistent indicator with three states: Saved on this device, Syncing, and Up to date. Users learned the vocabulary within a week, and support tickets about "lost" inspections dropped by 70%.

The lesson generalizes: people tolerate delay remarkably well. What they don't tolerate is uncertainty.

What we would do differently

We would have invested in tooling for inspecting the outbox far earlier. A tiny debug panel that shows pending mutations, retry counts and the last server error would have saved us weeks of guesswork during the beta. We'd also have tested on throttled connections from day one instead of treating it as a QA step.

Closing thoughts

Building for the slow network forced us to build a better app for everyone. The same architecture that keeps an inspector productive in a basement makes the app feel instant on office Wi-Fi. If you take one thing from this post, let it be this: design your data flow as if the network will fail, and you'll rarely be surprised when it does.
