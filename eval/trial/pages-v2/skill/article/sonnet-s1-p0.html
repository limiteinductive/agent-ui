The Quiet Craft of Resilient Interfaces

Most interface bugs are not clever. They are small assumptions about width, language, speed and attention that quietly stop being true. Here is how we design for the moments when they break.

Mara Lindqvist November 14, 2026 · Staff Frontend Engineer

Every team has a screenshot of the day their beautiful dashboard met a real user: a 360px phone, a name with forty characters, a connection that took eleven seconds. The design had not been wrong, exactly. It had simply never been asked a hard question.

Resilience is the habit of asking those questions early. It is less about heroic engineering and more about a handful of defaults that make the right outcome the easy one.

Start with the narrowest screen

Designing the smallest viewport first forces a ranking of what matters. If the title, the byline and the primary action fit in 360 pixels, the desktop layout is an act of generosity rather than a rescue mission.

Wide layouts then become additive: a second column, a larger measure, a sidebar. Nothing essential lives only in the space you gained.

“A layout that survives the worst content on the smallest screen has already survived most of what the world will throw at it.”

Let content decide the shape

Fixed pixel breakpoints age badly. Prefer layouts that respond to the space they are actually given: grids that drop columns when tiles get too small, rows that stack when they cannot fit, rails that scroll rather than squash.

  • Let text wrap; never assume a label is one word.
  • Give media an intrinsic ratio so nothing jumps when it loads.
  • Prefer gaps over margins so spacing stays predictable.

Make failure states first-class

Images fail. Requests time out. Lists come back empty. Each of these deserves a deliberate design, not a blank rectangle. A short message and a clear next step turns a dead end into a pause.

A small, honest retry helper

Retrying is only kind if it is bounded and polite. This helper backs off exponentially, adds jitter, and gives up with a useful error.

async function fetchWithRetry(url, { retries = 3, base = 300 } = {}) {
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      const res = await fetch(url);
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      return await res.json();
    } catch (err) {
      if (attempt === retries) throw err;
      const delay = base * 2 ** attempt + Math.random() * 100;
      await new Promise((r) => setTimeout(r, delay));
    }
  }
}

Measure what you ship

Resilience is a claim, and claims need evidence. Resize the window, throttle the network, paste in the longest name you can find. Automated checks catch overflow and broken images; your own eyes catch the rest.

Do this before launch, then again after. The interface your users meet is rarely the one you tested, and the gap between them is where the interesting work lives.
