The Quiet Cost of Layout Shift: Building Pages That Hold Still

Content that jumps while you read is more than an annoyance. It costs clicks, trust and sometimes money. These are the habits that keep a page still from the first paint onward.

Maya Okafor Staff Frontend Engineer · November 18, 2026

Last spring our checkout team noticed something odd in the analytics: a small but stubborn share of users were tapping "Remove item" when they clearly meant to tap "Continue". Session replays told the story within an hour. A promotional banner loaded late, pushed the cart down by 64 pixels, and placed the wrong button under a thumb already on its way to the screen.

Nobody had written a bug. Every component worked in isolation. The problem lived in the space between components, in the timing of when each one learned how big it was going to be.

Why layout shift happens

The browser lays out a page with whatever it knows at the moment. If an image has no intrinsic size, it gets zero height until the bytes arrive. If a web font has different metrics than its fallback, every line of text reflows when it swaps in. If a script injects a banner above existing content, everything below it moves.

Each of these is reasonable on its own. Together, on a slow connection, they turn the first five seconds of a page into a slide puzzle.

  • Unsized media: images, iframes and videos without dimensions or an aspect ratio.
  • Late-injected content: ads, cookie banners, "you might also like" modules.
  • Font swaps: fallback and web font with mismatched ascent, descent or width.
  • Animations on layout properties: transitioning height or top instead of transform.

“A page that holds still is a page that respects the reader’s attention. Every shift is a small interruption you didn’t mean to make.”

Reserve space before you need it

The single highest-leverage fix is telling the browser how big things will be before they load. For images this is as simple as including width and height attributes. Modern browsers use them to compute an aspect ratio immediately, even when CSS later scales the image.

For content whose size you can't know in advance, like a personalized recommendation strip, reserve a minimum height and let the content fill it. A slightly-too-tall placeholder is far less disruptive than a jump.

Measuring it in the field

Lab tools catch the obvious cases, but real users on real networks find the rest. We log every shift with its source element so we can tell which component caused it:

// Report layout shifts with the element that moved
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.hadRecentInput) continue; // user-caused, ignore

    const sources = entry.sources?.map((s) => ({
      node: s.node?.nodeName ?? "unknown",
      id: s.node?.id || null,
      delta: s.currentRect.y - s.previousRect.y,
    }));

    navigator.sendBeacon("/rum/cls", JSON.stringify({
      value: entry.value,
      page: location.pathname,
      sources,
    }));
  }
});

observer.observe({ type: "layout-shift", buffered: true });

Within a week this surfaced three culprits we had never seen in testing: a currency selector that rendered after geolocation resolved, a review-stars widget, and the very promo banner that started it all.

Tame your fonts

Font swaps are the sneakiest source of shift because they touch every line of text. The fix is to make the fallback look as much like the final font as possible. The size-adjust, ascent-override and descent-override descriptors let you tune a local fallback so that when the web font arrives, line breaks stay exactly where they were.

If a font isn't critical to the brand, consider font-display: optional. On a fast connection users get the web font; on a slow one they keep the fallback and nothing moves.

Make it part of the definition of done

Our final change was cultural rather than technical. Every new component now ships with a note describing its loading states: what it renders before data arrives and how big that is. Reviewers check it the same way they check accessibility labels.

Six months on, our 75th-percentile CLS sits comfortably under 0.05, and the mysterious "Remove item" taps are gone. The page holds still. It turns out readers notice, even if they can't say why.
