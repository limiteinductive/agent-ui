Why your incremental build is still slow

A practical tour of dependency graphs, cache keys, and the one environment variable that quietly invalidates everything.

Maya Okafor Senior Build Engineer · November 18, 2026 · 9 min read

Every engineering team eventually hits the same wall. The incremental build used to take eight seconds. Now a one-line change to a comment rebuilds half the monorepo, and nobody can explain why. The usual suspects get blamed first: a slow linter, a flaky CI runner, a cache server that is probably down again.

In most cases the real problem is simpler. The build system is doing exactly what it was told to do, and what it was told is too broad. This article walks through how incremental builds decide what to rebuild, where those decisions go wrong, and how to find the culprit in an afternoon.

How incremental builds decide what to rebuild

Incremental builds rest on a dependency graph. Each node is a unit of work, such as compiling a file, bundling a package, or running a test suite. Each edge says that one node needs the output of another. When something changes, the system walks the graph and marks every downstream node as stale.

Staleness alone is not enough, though. A node is only skipped when its cache key matches a previous run. The cache key is a fingerprint of every input that could affect the output. If any input differs, the cached result is thrown away and the work runs again.

What goes into a cache key

Most people assume a cache key contains only the source files for a target. In practice it usually contains much more: the lockfile, the compiler version, build flags, and any environment variables the tool has been told to respect. Forgetting one of these causes stale output. Including too many causes needless rebuilds.

A cache that is too conservative is slow. A cache that is too aggressive is wrong. Most teams spend their time on the first problem and get bitten by the second.

Maya Okafor, in a design review

The environment variable that breaks everything

The most common cause of surprise rebuilds is an environment variable that leaks into the key without anyone noticing. A developer sets BUILD_TIMESTAMP in a shell profile, or CI injects a commit SHA into a version string, and suddenly every target is unique on every run.

The fix is to make the environment allowlist explicit. Only variables that genuinely change the output should participate in the hash. Everything else should be ignored by default.

// Cache key = hash of every input that can change the output
const key = hash([
  ...sourceFiles,
  lockfileContents,
  toolchainVersion,
  ...envAllowlist.map((name) => name + "=" + (process.env[name] ?? "")),
]);

// BUILD_TIMESTAMP is deliberately absent from envAllowlist.

Notice what is missing from the list. Timestamps, hostnames, and CI job IDs are useful for logging but harmful for caching. Keep them out of the key and your hit rate usually recovers within a single day.

Finding the culprit in an afternoon

Guessing is expensive. Instead, run the same build twice with logging turned on and diff the two cache key manifests. The manifests list every input that went into each key. Any line that differs between runs is a candidate for the bug.

Once you have a candidate, verify it by removing it temporarily and checking whether the hit rate changes. If it does, you have found your problem. If it does not, repeat the diff with a different pair of runs, since the cause is often intermittent.

Common culprits

In our experience, four causes account for almost every case we have investigated:

  • Absolute paths embedded in generated files, which differ between laptops and CI.
  • Unsorted file lists, where directory traversal order changes across operating systems.
  • Generated code that includes a random seed or a build date.
  • Plugins that read the system clock or the current user name.

Keeping it fast over time

A fixed cache key is not the end of the story. Build graphs drift as teams add packages and dependencies. A rule that was reasonable last year can become a bottleneck this year. Schedule a quarterly review of your largest targets and check whether their inputs still match what you expect.

It also helps to measure the hit rate as a first-class metric. Put it on the same dashboard as test duration and deploy frequency. When it drops, someone should be notified the same way they would be for a failing test.

Closing thoughts

Incremental builds are a promise: if nothing relevant changed, nothing needs to run. Slow builds are usually a sign that the promise is being kept too loosely. Tighten the inputs, make the allowlist explicit, and measure the results. The eight-second build is still within reach.
