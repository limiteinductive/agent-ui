Designing for Slow Networks: Lessons from Shipping to 2G

What we learned rebuilding a checkout flow for users on patchy connections, and why every team should test on a throttled phone at least once a week.

Maya Okafor Staff Engineer, Web Platform · November 14, 2026

Last spring our analytics showed something uncomfortable: nearly a third of abandoned checkouts came from sessions where the first meaningful paint took longer than eight seconds. These weren't edge cases. They were people on prepaid data plans, commuters passing through tunnels, and customers in regions where 3G is still the norm rather than the fallback.

We had been building on fibre and testing on flagship phones. Our users were not. This article walks through the changes we made over six months, which ones mattered, and which ones turned out to be cargo cult.

Start by measuring the real thing

Lab tools are useful, but they lie politely. Lighthouse runs on a simulated throttle that smooths out the jitter and packet loss that make real slow networks so painful. We started collecting field data with the PerformanceObserver API and bucketing it by effective connection type.

The results reshaped our priorities. On fast connections, JavaScript execution dominated. On slow ones, the number of round trips before first render mattered far more than the total bytes.

The round-trip budget

On a 2G connection, a single round trip can take 300–800 milliseconds. Every redirect, every DNS lookup to a new origin, and every render-blocking stylesheet costs at least one. We set a hard budget: the critical path may not exceed three round trips after the HTML arrives.

“Bytes are a cost you pay once. Round trips are a tax you pay on every hop, and slow networks charge interest.”

— From our internal performance guidelines

Ship less, but ship it sooner

Our biggest single win was inlining the critical CSS and deferring everything else. The second was moving third-party scripts behind user interaction. Here is the small helper we used to load non-essential scripts only once the main thread is idle and the network is not saturated:

function loadWhenIdle(src) {
  const conn = navigator.connection;
  const slow = conn && /2g/.test(conn.effectiveType);

  const inject = () => {
    const s = document.createElement('script');
    s.src = src;
    s.async = true;
    document.head.append(s);
  };

  if (slow) {
    // Wait for the first user interaction on slow links.
    addEventListener('pointerdown', inject, { once: true });
  } else if ('requestIdleCallback' in window) {
    requestIdleCallback(inject, { timeout: 4000 });
  } else {
    setTimeout(inject, 2000);
  }
}

loadWhenIdle('/js/chat-widget.js');

This one change cut median time-to-interactive on 2G sessions by 41%. The chat widget, it turned out, was rarely opened before someone had already scrolled the page.

Images: the honest trade-off

We adopted responsive images with srcset and modern formats, and lazy-loaded everything below the fold. But we also learned to resist the urge to lazy-load the hero image. Doing so delayed the largest contentful paint by a full round trip, which on slow networks is exactly the wrong trade.

Design for the in-between states

Fast networks hide your loading states. Slow networks put them on stage. We audited every interaction for three questions:

  • What does the user see if this takes ten seconds?
  • Can they tell the difference between “loading” and “broken”?
  • If the request fails, do they lose what they typed?

The third question surfaced the most bugs. Our address form cleared itself on a network error. Fixing it took an afternoon and recovered a measurable slice of revenue.

What didn't matter (as much as we thought)

We spent two weeks shaving kilobytes off our icon set. It made no measurable difference, because the icons were already cached for returning visitors and not on the critical path for new ones. Measure before you optimize, and measure again after.

Make it a habit

Performance work decays. Every new feature is a chance to regress. We now run a weekly “slow Friday” where the team uses the product on a throttled mid-range Android phone for an hour. It is humbling, occasionally maddening, and the single most effective practice we've adopted.

If you only take one thing from this article: go find the slowest device in your office, turn on network throttling, and try to buy something from your own site.
