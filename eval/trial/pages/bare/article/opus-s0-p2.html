The Quiet Cost of Premature Abstraction

Why the cleverest code in your repository is often the hardest to change, and how to tell when duplication is actually the right call.

Maya Okafor Staff Engineer · November 18, 2026

Three years ago, our team shipped a "universal" data-fetching layer. It handled retries, caching, pagination, optimistic updates, and offline sync behind a single elegant interface. It was, by most accounts, beautiful. It was also the reason a two-line bug fix took us eleven days last spring.

This isn't a story about bad engineers. Everyone involved was thoughtful and experienced. It's a story about how good instincts — don't repeat yourself, design for the future, make things reusable — can quietly compound into a codebase that resists change.

The rule of three, revisited

Most of us learned some version of the rule of three: tolerate duplication twice, abstract on the third occurrence. It's decent advice, but it hides an assumption — that the three occurrences are actually the same thing. Often they merely look alike today.

Two functions that format currency for an invoice and for a dashboard widget share ninety percent of their code. Then finance asks for accounting-style negatives on invoices only, and product wants abbreviated values ("$1.2M") on the dashboard. Now your shared helper grows flags, and every flag doubles the number of states you need to reason about.

“Duplication is far cheaper than the wrong abstraction. You can always merge two things later; untangling one thing into two is surgery.”

— a lesson we paid for in sprint time

What a bad abstraction looks like

The warning signs tend to arrive gradually. A boolean parameter appears. Then an options object. Then a callback that lets callers override "just this one step." Here's a lightly anonymized excerpt from our old fetching layer:

export function useResource<T>(key: string, opts: ResourceOptions<T> = {}) {
  const {
    retry = 3,
    paginate = false,
    optimistic = false,
    skipCacheIf,          // added for checkout
    transformBeforeCache, // added for search
    legacyMode = false,   // do not remove: billing
  } = opts;

  if (legacyMode && paginate) {
    // TODO: this combination is "unsupported" but billing uses it
    return useLegacyPaginated(key, opts);
  }
  // ...340 more lines
}

None of these options were unreasonable on their own. Together they formed a matrix of behaviors no one could hold in their head. Tests covered the common paths; production found the rest.

A healthier default

We didn't replace the layer with a better abstraction. We replaced it with several small, boring hooks, each owned by the feature that used it. Shared pieces — a retry helper, a cache key builder — stayed shared because they were genuinely identical in intent, not just in shape.

  • Abstract behavior, not appearance. Ask whether two pieces of code change for the same reasons.
  • Prefer composition over configuration. Small functions callers can combine beat one function with twelve flags.
  • Make inlining cheap. If an abstraction is easy to delete, it's safe to try.
  • Watch for flags. The first boolean parameter is a signal to pause, not a feature request.

Measuring the change

Six months later, median time-to-merge for data-layer changes dropped from 4.2 days to 1.1. Line count went up by about 18%. We consider that a bargain: the extra lines are obvious, local, and owned.

Closing thoughts

Abstraction is one of the most powerful tools we have, which is exactly why it deserves restraint. The next time you feel the pull to unify, write the second copy instead, and wait to see whether the two versions drift apart. Often, they will — and you'll be glad you let them.
