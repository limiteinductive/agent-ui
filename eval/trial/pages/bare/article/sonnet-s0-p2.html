The Quiet Revolution of Container Queries

Why components, not pages, should decide how they look, and how to start using that idea today.

 Maya Lindqvist November 18, 2026 · 9 min read

For more than a decade, responsive design has meant one thing: asking the browser how wide the viewport is. It worked, because pages were the unit of design. But we no longer build pages. We build components, and a component rarely knows where it will end up.

A product card might live in a three-column grid, a narrow sidebar, or a full-width hero. Media queries can't tell it which. Container queries can.

The problem with viewport thinking

Imagine a card with an image on the left and text on the right. On a wide screen that looks great in the main column. Drop the same card into a 280px sidebar on that same wide screen and it falls apart. The viewport is huge, but the space available to the card is tiny.

The traditional fix is a pile of modifier classes: .card--compact, .card--sidebar, .card--stacked. Every new context means another variant, and every variant is a chance for drift.

“A component should respond to the space it is given, not to the screen it happens to be on.”
Maya Lindqvist

Enter the container

Container queries flip the relationship. You mark an element as a containment context, then write rules that respond to that element's size. The card becomes self-aware, and the layout logic lives next to the component it belongs to.

.card-wrapper {
  container-type: inline-size;
  container-name: card;
}

.card {
  display: grid;
  gap: 1rem;
}

@container card (min-width: 480px) {
  .card {
    grid-template-columns: 160px 1fr;
    align-items: center;
  }
}

That's the whole idea. The wrapper declares itself a container, and the card adapts once there are 480 pixels to work with, regardless of the viewport.

Practical tips for adoption

You don't need to rewrite your design system. Start with the components that appear in the most varied contexts: cards, media objects, navigation lists, and data tables. Wrap them, name the containers, and replace the most brittle media queries first.

  • Prefer inline-size containment; it avoids height-related surprises.
  • Name your containers so nested components don't query the wrong ancestor.
  • Keep media queries for page-level concerns like navigation and global spacing.
  • Use container query units such as cqi for fluid typography inside components.

What it changes about design

The biggest shift is cultural. Designers can hand over components with defined behaviors at each size, instead of page mockups at three breakpoints. Engineers can test a component in isolation and trust that it will behave the same in production. Documentation tools can show a component at any width without resizing the browser window.

Container queries are not flashy. Nothing animates, nothing glows. But they quietly remove an entire category of layout bugs, and that is the best kind of revolution.
