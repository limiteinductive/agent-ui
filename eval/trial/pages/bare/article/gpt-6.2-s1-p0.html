Write down why you changed it

A short note can save the next engineer an afternoon of archaeology.

Maya Chen · August 18, 2026

Last winter I opened a pull request to shorten a cache lifetime. The value was five minutes. I wanted thirty seconds. A teammate asked why we had picked five minutes in the first place, and neither of us could answer. We found the original change in Git, followed it to a closed issue, and finally dug up a dashboard screenshot in an incident thread. By then, the change itself had taken about ten minutes and the investigation had taken most of the afternoon.

Keep the part Git can’t tell you

The diff told us when the value changed and who changed it. The screenshot explained why. A slow upstream endpoint used to receive a burst of requests every time the cache expired. Five minutes gave it enough breathing room during the morning traffic peak. The endpoint had been replaced since then, so we could retire the workaround once we verified that the new service handled misses comfortably.

When you make a choice like that, write down the condition that drove it. A latency measurement, an upstream rate limit, or a promise to a customer can each explain why a reasonable team settled on a particular value. Name the condition specifically enough that someone can check whether it still applies.

“The most useful sentence in a decision note tells the next engineer when to revisit it.”

Put the reason where someone will look

For a single setting, a comment beside the value is a good place to start. The person who wants to change it will see the context while editing. For a decision that spans several files, give the explanation a stable home and link to it from the relevant entry point. The pull request can hold the longer discussion, including the measurements and alternatives the team considered. 

// Five minutes limits peak traffic to the legacy endpoint.
// Revisit after the replacement handles a full morning peak.
const cacheTtlSeconds = 5 * 60;

Two lines are enough here. They explain who benefits from the longer lifetime and give the next engineer a concrete event to check. If the service has several dashboards, link to the one you used in the pull request so the next person can compare their measurements with yours.

Start with the choices reviewers ask about

The easiest time to capture a reason is when a reviewer asks for it. If someone says “Why this timeout?” or “What happens if we remove this retry?”, answer in the thread and put the durable part of the answer near the code. That way the explanation reaches both the person reviewing today and the person editing six months from now.

On my next pull request, I’m spending the last minute looking for one choice that would be hard to explain from the diff alone. If I find one, I’ll leave a sentence about what led to it and what would make me change my mind.
