The Quiet Return of Server-Rendered Interfaces

After a decade of shipping ever-larger JavaScript bundles, teams are rediscovering the HTML-first web. Here is what changed, what we learned, and how to decide what is right for your product.

Maya Lindqvist November 14, 2026 · 9 min read

For most of the 2010s, the answer to "how do we build this interface?" was a single-page application. Ship a shell, fetch JSON, render everything in the browser. It gave us fluid navigation and a clean separation between API and UI. It also gave us loading spinners, hydration mismatches, and a performance budget that quietly ballooned with every sprint.

Today the pendulum is swinging back. Not to the page-reload-on-every-click web of 2005, but to something more nuanced: servers that render meaningful HTML, and clients that enhance it only where interactivity truly earns its cost.

Why the pendulum swung

Three forces converged. First, device reality: the median phone is far slower than the laptops developers use, and parsing a megabyte of JavaScript is expensive there. Second, the tooling matured: streaming rendering, partial hydration, and edge runtimes made server output fast and composable. Third, teams grew tired of duplicating logic, such as validation, routing, and data shaping, across two runtimes.

Rule of thumb: if a component never changes after the first paint, it should never ship JavaScript to the browser.

What "HTML-first" actually means

It does not mean abandoning components. It means treating the network response as the primary product and the client runtime as progressive enhancement. A form should submit without JavaScript. A link should navigate without a router. Then, and only then, do you layer on optimistic updates and transitions.

The fastest code is the code you never send. The most reliable interface is the one that works before your bundle finishes downloading.

— Maya Lindqvist

A small example

Consider a comment form. In the HTML-first approach, the server owns validation and the browser simply posts the form. A tiny enhancement intercepts the submit to avoid a full reload, and falls back gracefully if it fails to load.

// Progressive enhancement for a plain HTML form
const form = document.querySelector('form[data-enhance]');

form?.addEventListener('submit', async (event) => {
  event.preventDefault();
  const response = await fetch(form.action, {
    method: form.method,
    body: new FormData(form),
    headers: { 'X-Requested-With': 'fetch' },
  });

  if (response.ok) {
    const html = await response.text();
    document.querySelector('#comments').innerHTML = html;
    form.reset();
  } else {
    form.submit(); // fall back to a normal navigation
  }
});

Notice that the enhancement is under twenty lines and contains no framework. If it fails, the user still gets a working product.

The trade-offs nobody mentions

Server rendering is not free. You pay in server compute, in cache invalidation complexity, and in the mental overhead of deciding where each piece of state lives. Highly interactive tools, such as design editors, spreadsheets, and real-time dashboards, still benefit enormously from rich client-side architecture.

The key is to choose deliberately. Ask what each screen is for: reading, browsing, or manipulating. Reading and browsing lean toward the server. Manipulating leans toward the client. Most products contain all three, and the best ones mix them without ceremony.

Where to go from here

Start small. Pick one content-heavy route, measure its current weight and interaction latency, and rebuild it with server-rendered HTML and a sprinkle of enhancement. Compare the numbers. In our experience the results make the next decision easy.
