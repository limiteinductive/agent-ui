Building Resilient Frontends: Lessons from Shipping Offline-First Apps

Our field technicians work in basements, elevators, and rural substations. Here is how we rebuilt our scheduling app so it never blocked on the network, and what broke along the way.

Maya Okafor November 18, 2026 · 9 min read

For most of the app's first two years, every screen assumed a working connection. Loading a work order meant a request. Submitting a checklist meant a request. When a request failed, the user saw a spinner that never resolved, and the technician often drove to the next job with unsaved notes.

The rebuild started with one rule: the local device is the source of truth for anything the user is currently doing. The server is a peer that we sync with when we can.

Start with the data model, not the screens

We spent the first three weeks mapping every entity a technician touches: work orders, asset records, photos, signatures, and time entries. For each one we answered three questions. Who can create it offline? Who can edit it? And what happens when two people change it at once?

Most conflicts turned out to be rare. Two technicians editing the same asset note at the same time happened maybe once a month. Photo uploads were the opposite: they were common, large, and almost never conflicted, so they needed a separate queue with aggressive retry.

Offline support is not a feature you bolt onto a request-driven app. It changes what the app considers a save, a success, and a failure.

Internal design review, March 2026

Writes go to a local outbox

Every mutation is written to a local store first and appended to an outbox. The UI updates immediately. A background worker drains the outbox when connectivity returns, and each entry carries an idempotency key so a retry after a dropped response can never create a duplicate work log.

The core of the outbox looks roughly like this:

async function enqueueChange(store, change) {
  const entry = {
    id: crypto.randomUUID(),
    createdAt: Date.now(),
    attempts: 0,
    ...change,
  };

  await store.outbox.add(entry);
  store.emit('outbox:changed');
  return entry.id;
}

async function drainOutbox(store, api) {
  for (const entry of await store.outbox.all()) {
    try {
      await api.send(entry.endpoint, entry.payload, {
        idempotencyKey: entry.id,
      });
      await store.outbox.remove(entry.id);
    } catch (err) {
      if (!isRetryable(err)) {
        await store.outbox.markFailed(entry.id, err);
        continue;
      }
      await store.outbox.incrementAttempts(entry.id);
      break; // stop draining; back off until the next online event
    }
  }
}

The break on retryable errors matters more than it looks. Without it, a flaky connection fires dozens of requests in a row, each one timing out, and the worker never reaches a stable state.

Show sync state, don't hide it

Early testers said the app felt "fine" but they did not trust it. Nothing told them whether their work had left the device. We added a small status line to every screen: saved on device, syncing, or needs attention. Entries that failed permanently surfaced in a list the technician could resolve with one tap.

That single change cut support tickets about "lost" work by more than half in the first month. Users do not need the app to be magically online. They need to know where their data is.

What we would do differently

We underestimated how much storage the photo cache would consume on older devices. We also shipped the first sync engine without a way to inspect the outbox from the support tools, which made debugging customer reports slow. Both are fixed now, but both should have been in the first version.

If you are considering this kind of rebuild, start by listing the operations your users perform when the network is worst, not when it is best. Those are the paths that define your architecture.
